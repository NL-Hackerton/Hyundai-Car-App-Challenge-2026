## 1. 앱 한 줄 소개

문별 하차 준비는 두 사람이 반려견·짐의 준비를 나누는 외출에서, 앞좌석 확인 담당자가 실제 문 개방 변화에 연결된 미확인 항목을 다시 찾아 준비를 이어가도록 돕는 Pleos 차량용 앱이다.

## 2. 기획 배경

### 한 사람이 안에 남아 확인하는 동반 외출

[가정·설계] 초기 고객은 반려견과 함께 외출한 두 사람 가운데 한 명이 앞좌석에 남아 확인을 맡고, 다른 한 명이 후석 양쪽 문에서 이동장·가방·의료용품을 챙기는 사용자다. 앞좌석에서는 후석 문 안쪽과 바닥이 잘 보이지 않으며, 동승자가 한쪽 문에서 다른 쪽으로 옮기면 확인 담당자는 말로만 상태를 확인해야 한다. 본 앱은 이 중단·복귀 순간에 관측된 문 개방과 그 문에 남은 미확인 항목을 한 화면에 연결한다. 실제 준비 여부는 두 사람이 말로 확인하고, 앞좌석 사용자가 직접 기록한다.

문제가 「어느 문에서 무엇을 했는지 잠깐 헷갈리는」 수준에 그치지 않는 이유는, 후석 준비가 한 번에 완료되지 않고 문 사이 왕복과 시간 압박이 겹치기 때문이다. 아래 장면은 초기 가설을 설명하기 위한 [가정·설계] 예시이며, 발생 빈도는 발견 조사로 확인한다.

- **동물병원 방문, 긴장한 중·대형견.** 주차 후 한쪽 문에는 이동장과 기저귀·물티슈가, 반대쪽에는 진료비·진료기록·목줄·배변봉투가 나뉜다. 반려견이 보채면 동승자는 이동장 쪽을 먼저 열고 달랜 뒤, 접수에 필요한 가방을 챙기러 반대쪽으로 이동한다. 앞좌석 담당자는 병원 입구와 시계를 보며 「이동장 잠금은 됐고, 목줄은? 진료기록은?」을 되묻게 된다. 문이 바뀌는 순간마다 미확인 항목이 섞이면, 말로만 확인하는 부담이 증가한다.
- **비 오는 날, 한쪽만 열 수 있는 주차.** 옆 차량이나 벽 때문에 후석 한쪽 문만 열린다. 동승자는 열린 쪽에서 이동장 주변 용품을 챙긴 다음, 차를 조금 빼거나 돌아가 반대쪽 문을 연다. 비에 젖지 않으려 서두르는 동안 앞좌석에서는 닫힌 쪽의 남은 항목이 보이지 않는다. 문이 바뀌는 맥락을 화면에 남겨 두지 않으면, 확인 담당자는 방금 완료한 쪽과 아직인 쪽을 다시 물어야 한다.
- **아이와 반려견을 함께 태운 외출.** 앞좌석 한 사람은 아이의 하차·안전벨트를 살피며 자리를 비우기 어렵고, 다른 한 사람이 후석 양쪽을 오가며 유모차 가방과 반려견 용품을 배분한다. 동시에 두 문이 잠깐 열리거나, 한쪽을 열어 둔 채 반대쪽으로 옮기는 일이 이어지면, 앞좌석에서는 「지금 어느 문 기준으로 확인해야 하는지」가 중단된다.
- **무거운 짐과 반대쪽 소형 물품.** 한쪽에는 이동장과 담요처럼 무게가 있는 준비가, 다른 쪽에는 간식·약·여분의 목줄처럼 빠지기 쉬운 소형 물품이 있다. 무거운 쪽을 먼저 내린 뒤 소형 물품을 잊고 문을 닫으면, 병원·산책 입구에서 다시 차로 돌아오는 왕복이 발생한다. 앱은 문을 닫았다고 항목을 완료하지 않으며, 앞좌석 확인이 완료되기 전까지 미확인으로 남긴다.

이 기획에서 차량 화면을 쓰는 이유는 모든 탑승자가 큰 화면을 보기 때문이 아니다. 확인 담당자가 이미 앞좌석에 남는 흐름에서, 관측된 문 변화와 중단한 준비 항목을 한곳에 두기 위해서다. 혼자 모든 준비를 하는 사용자와 두 사람 모두 곧바로 차 밖으로 나가는 사용자는 초기 대상에서 제외한다. 실제 환경에서 후석 두 영역의 문 상태 조회와 알림 수신이 지원되어야 하며, 운전석 문만 읽을 수 있는 환경은 같은 지원 대상으로 포함하지 않는다.

### 설정 부담을 줄이는 시작 방식

[가정·설계] 문별 항목을 매번 처음부터 입력하게 하면, 설치·협업 부담이 재탐색 이득을 상쇄할 수 있다. 따라서 초기 제품은 설정 단계를 아래처럼 짧게 둔다.

| 시작 방식 | 사용자 조작 | 앱의 처리 |
|---|---|---|
| 외출 유형 템플릿 | 병원·산책·여행 중 하나를 고른다. | 문별로 나뉜 기본 목록(각 최대 3개, 총 최대 6개)을 채운다. 사용자는 빠진 항목만 수정하거나 삭제한다. |
| 직전 목록 재사용 | 「지난번 그대로」를 고른다. | 직전에 확인을 마친 문별 배치를 불러온다. |
| 원탭 시작 | 템플릿 또는 직전 목록을 고른 뒤 시작을 누른다. | 플랫폼의 차량 화면 사용 제한을 확인한 다음, 문별 미확인 항목 화면으로 바로 들어간다. |
| 수동 조정(선택) | 주차 중 항목·문 배치만 수정한다. | 문별 설정 자체를 차별 기능으로 주장하지 않는다. |

<p>표 1. 계획한 사전 설정 완화.</p>

반려견 이동용품은 첫 템플릿으로 제안한다. 병원 템플릿에는 이동장·목줄·진료기록·배변봉투처럼 빠지기 쉬운 항목을, 산책 템플릿에는 물·간식·배변봉투를, 여행 템플릿에는 이동장·담요·여분 목줄을 기본값으로 둔다. 사용자가 정하는 준비물을 각 문에 두되, 앱이 이동장 개방이나 동물 하차를 지시하지 않는다. 물건·동물의 존재 감지, 방치 예방, 법적 준수 확인 또는 하차 안전 허가는 제공 범위가 아니다.

### 생활 집단의 근거와 확인할 수요

[문헌] 농림축산식품부가 2026년 2월 12일 발표한 「2025년 반려동물 양육현황조사」는 3,000가구 방문 면접조사이며, 반려동물 양육가구 비율은 29.2%, 양육가구 중 개 양육 비율은 80.5%다. 별도 「2025년 동물복지에 대한 국민의식조사」는 5,000명 온라인 조사이며, 반려견 외출 시 목줄·인식표·배설물 수거 등 준수사항을 잘 지킨다는 긍정 응답은 48.8%다.[14]

이 자료는 반려동물 외출 준비를 검토할 생활 집단과 정책적 관련성을 보여준다. 두 조사는 모집단과 조사 방법이 다르므로 비율을 곱해 시장 규모를 계산하지 않는다. 29.2%를 차량 동반 이동자나 Pleos 앱 고객 비율로 사용하지 않으며, 48.8%의 나머지를 실제 미준수율로 해석하지 않는다. 본 앱이 다루는 자연스러운 2인 분담 동선의 빈도와 중단 후 재탐색 부담은 발견 조사로 확인한다.

SDK는 차량 앱 개발에 필요한 소프트웨어 도구 모음이며, API는 앱이 차량 상태 등을 조회하는 호출 인터페이스다. 현재 수행한 범위는 공개 자료 조사와 기획이다. 사용자 모집·인터뷰·사용성 비교·SDK 실행은 아직 수행하지 않았다. 이하에 제시하는 기능·가격·전환율·개발 일정은 설계와 검증 계획이다.

## 3. 앱 주요 기능 및 차량 특화 요소

### 문 상태와 준비 확인을 분리하는 화면

[가정·설계] 초기 목록은 후석 두 영역에 각 최대 3개, 총 최대 6개 항목으로 제한한다. 두 그룹과 완료 버튼의 위치는 고정하며, 문 이벤트 때문에 목록을 자동 스크롤하거나 재정렬하지 않는다. 화면의 ‘문 열림’ 표시는 관측된 차량 상태이고, ‘선택한 확인 그룹’은 사용자의 선택이다. 두 표시를 구분하여 문 열림을 작업자 위치로 오해하지 않도록 한다.

| 기능 | 입력과 화면 처리 | 사용자 확인·복구 |
|---|---|---|
| 문별 준비 설정 | 병원·산책·여행 템플릿 또는 직전 목록으로 시작하고, 필요 시 지원되는 두 문에 준비물을 조정한다. | 주차 중 항목을 수정하며, 문별 설정 자체를 차별 기능으로 주장하지 않는다. 빈 목록을 매번 손으로 채우는 흐름은 기본값으로 두지 않는다. |
| 중단 항목 강조 | 자동 강조 모드에서 매핑된 지원 영역의 문 개방 이벤트가 관측되면 미확인 항목을 강조한다. | 개폐의 준비 관련성은 판별하지 못한다. 다른 그룹의 남은 항목도 유지하며, 닫힌 문을 완료로 바꾸지 않는다. |
| 고정 목록과 수동 선택 | 사용자가 고정된 그룹 제목을 누르면 그 그룹을 선택한다. | 해당 세션에서는 수동 선택이 우선한다. 다른 문 이벤트는 문 상태만 갱신한다. |
| 명시적 항목 기록 | 준비 확인 입력만 항목 상태를 바꾼다. | ‘사용자 확인’, ‘이번에는 해당 없음’, ‘미확인’을 구분한다. |
| 중단과 재개 | 사용자의 일시중지 선택, 앱 화면의 수명주기를 관리하는 Activity 중단 또는 차량 Service 연결 해제 시 세션을 일시 중지한다. | 담당자는 하차 전에 직접 일시중지를 선택한다. 재개 때 현재 제한과 문 상태를 다시 읽는다. |

<p>표 2. 계획한 사용자 기능과 확인 책임.</p>

두 문이 동시에 열리면 두 그룹의 문 열림을 함께 표시한다. 마지막 이벤트가 온 문 하나 때문에 다른 그룹을 숨기지 않으며, 중복 이벤트로 강조를 반복하지 않는다. 사용자가 ‘문 상태 강조 사용’을 다시 선택해야 자동 강조로 돌아간다. 두 문을 계속 열어 둔 채 사람이 이동하면 새 개방 이벤트가 없으므로 앱은 이동을 알 수 없다. 이 경우에도 고정 목록과 수동 선택으로 확인을 이어가되, 자동 강조의 이점이 없는 조건으로 검증 결과에 포함한다.

기기 내부에는 템플릿과 사용자 확인 상태만 저장한다. 계정·차대번호(VIN)·위치·음성·사진·동물 이름은 수집하지 않고 도어 원시 이력을 저장하지 않는다. 앱 안에서 저장 기록을 초기화할 수 있도록 계획한다. 차 밖 스마트폰 알림이나 차량 전원 종료 뒤 상시 구동은 제공하지 않는다.

### 직접 대안 대비 검증할 차이

[문헌] Apple Reminders는 목록 템플릿의 저장·재사용·공유를 제공하고[26], Google Keep은 체크박스·항목 재정렬·들여쓰기를 제공한다[27]. Microsoft To Do는 작업을 세부 단계로 나누고 완료와 중요도를 관리한다[28]. 반복 목록·단계 구분·완료 기록은 기존 대안의 강점이며 본 앱의 새로운 발명으로 제시하지 않는다.

| 직접 대안 | 이미 제공하는 강점 | 비교할 차이 |
|---|---|---|
| Apple Reminders | 반복 목록을 템플릿으로 저장하고 공유한다.[26] | 같은 항목을 둔 상태에서 중단한 미확인 항목을 다시 찾는 부담을 비교한다. |
| Google Keep | 체크박스와 항목 순서·들여쓰기를 관리한다.[27] | 수동 전환을 강제하지 않고 중단 항목 재탐색 시간을 비교한다. |
| Microsoft To Do | 세부 단계·완료·중요도를 관리한다.[28] | 차량 문 변화에 맞춘 강조가 실제 재탐색을 돕는지 비교한다. |
| 종이 목록·구두 협의 | 설치·계정·지원 차종 제한이 없고 작업자 가까이 둘 수 있다. | 두 문 사이에서 준비가 자연스럽게 중단·재개될 때만 추가 편익이 생기는지 확인한다. |

<p>표 3. 직접 대안의 강점과 본 앱의 비교 범위.</p>

세 목록 도구의 공식 문서에서 확인한 내용에는 실시간 차량 문 상태와 중단된 준비 항목을 문별 그룹으로 연결하는 기능에 관한 설명이 없다. 이를 모든 제품 버전에서 해당 기능이 없다는 주장으로 확대하지 않는다. 핵심 차별 가설은 자동 강조가 기존 목록과 같은 준비물을 두고도 중단 후 첫 미확인 항목을 더 빨리 찾게 하는지다. 화면 크기나 기존 도구에 없는 불편을 인위적으로 만들어 얻은 차이는 차량 연동의 기여에서 제외한다.

차량의 기존 기능과도 역할을 나눈다. Hyundai Bluelink는 공식 소개에서 도어·트렁크 상태 조회 등을 제공한다.[11] Advanced Rear Occupant Alert는 실내 움직임 감지·알림, Safe Exit Assist는 후방 접근 차량 경고와 조건부 차일드록 기능을 설명한다.[13] 본 앱은 상태 조회나 안전 경고를 대체하는 대신 사용자 준비 항목의 중단·복귀에 집중한다. 인용한 해외 설명을 국내 차종의 동일 사양으로 간주하지 않는다.

## 4. 주요 사용 시나리오

### 두 문 사이에서 중단된 준비를 이어가는 장면

[가정·설계] 두 보호자가 중형견과 동물병원 예약을 위해 주차하였다. 옆 차량 때문에 후석 한쪽 문만 먼저 열리며, 한 명은 앞좌석에서 아이와 준비 확인을 맡고 동승자는 열린 쪽에서 이동장·기저귀를 확인한 뒤 접수 가방을 챙기러 반대쪽 문으로 돌아간다. 앞좌석에서는 후석 문 안쪽과 바닥이 잘 보이지 않으므로, 문이 바뀌는 동안 「이동장은 됐고 목줄·진료기록은 아직인지」를 말로만 확인하면 누락과 차 안 왕복이 발생하기 쉽다. 앱은 사용자가 병원 템플릿 또는 직전 목록으로 원탭 시작하며, 내비게이션 도착이나 문 열림으로 자동 실행하지 않는다.

| 단계 | 사람의 행동 | 앱의 응답 |
|---|---|---|
| 사전 설정 | 주차 후 「병원」 템플릿을 고르거나 「지난번 그대로」로 시작한다. 필요하면 항목만 수정한다. | 읽기 가능한 두 후석 영역에 총 최대 6항목을 연결한다. 매번 빈 목록부터 채우지 않는다. |
| 시작 | 앞좌석 담당자가 원탭으로 앱을 연다. | 플랫폼의 차량 화면 사용 제한을 확인한 뒤 문별 미확인 항목을 표시한다. |
| 첫 문 작업 | 동승자가 열린 후석 문에서 이동장 쪽을 준비한다. | 관측된 문 그룹을 강조한다. 담당자는 말로 확인한 항목만 완료한다. |
| 중단·이동 | 접수 가방이 반대쪽에 있어 동승자가 돌아 반대쪽 문을 연다. 앞좌석에서는 후석 바닥이 보이지 않는다. | 새 그룹을 강조하고 첫 그룹의 「남은 준비」를 유지한다. 닫힌 문을 완료로 바꾸지 않는다. |
| 복귀 | 반려견이 보채 동승자가 첫 문으로 돌아온다. | 문이 다시 열리면 미확인 항목을 강조한다. 계속 열려 있었다면 자동 이동 추정 없이 수동 선택을 제공한다. |
| 종료 | 동승자가 실제 준비 완료를 알린다. 잊은 목줄·진료기록이 있으면 미확인으로 남아 왕복을 줄인다. | 담당자가 항목 상태를 확인하고 세션을 직접 종료한다. |

<p>표 4. 화면 접근이 유지되는 2인 동반 외출 시나리오.</p>

미확인 항목은 문을 닫아도 미확인 상태로 남는다. 자동 강조 모드에서는 매핑된 지원 영역의 개방 이벤트를 반영하므로 준비와 무관한 개폐도 강조될 수 있다. 앱이 관련성을 판별하지는 않으며, 원치 않은 강조 횟수를 사용자 가치 검증에서 측정한다. 수동 그룹을 선택한 상태에서는 모든 문 이벤트가 문 상태만 갱신하고 선택한 그룹을 바꾸지 않는다.

앞좌석 담당자는 하차 전에 직접 「일시중지」를 선택한다. 앱은 사람의 실제 하차·탑승자 존재를 감지하지 않는다. Activity가 중단되거나 차량 Service 연결이 해제되면 진행을 일시 중지한다. 재개 때 현재 상태를 다시 조회하며, 문 열림이나 지난 완료 기록만으로 준비가 완료되었다고 안내하지 않는다.

플랫폼의 차량 화면 사용 제한이 변경되면 준비 확인보다 제한을 우선한다. 화면을 사용할 수 없는 상태에서는 주행 중 사용 최적화를 선언하지 않은 화면을 닫거나 이탈시킨다. 이 선언과 제한 조회의 기술 계약은 5항에서 설명한다. 사용자는 주변 교통과 실제 준비 상황을 별도로 판단한다.

## 5. 개발 계획

### 개발 환경과 최소 API

[문헌] 개발 시작 기준은 공식 Vehicle SDK Sample App 문서의 Vehicle SDK 2.3.2, Vehicle Service 2.3.22, Pleos_Connect_v2.1 Android 14, JDK 17, Gradle 8.10.2, Android Gradle Plugin(AGP) 8.8.2, Kotlin 2.0.0, compile/targetSdk 35다.[6] 제품 앱의 minSDK는 공식 설치 안내에 따라 28 이상으로 계획한다.[3] 의존성 안내의 `ai.pleos.playground:Vehicle:2.3.2`를 기준으로 삼는다.[9] 이전 릴리스의 2.3.1과 혼합하지 않고 실제 받은 SDK·Service·가상 기기 버전과 설치 결과를 기록한다.

[가정·설계] 차량 입력은 Door 읽기 한 도메인과 플랫폼의 차량 화면 사용(UX) 제한 정보로 좁힌다. capability는 기능·영역별 접근 수준과 허용 값 범위를 확인하는 정보다. 실제 `READ` 또는 `READ_WRITE`인 영역만 사용한다.[4] SDK 접근 및 읽기 권한은 공식 협의·승인 절차에 따른다.[1]

| 용도 | 공개 API·권한 | 구현 시 적용할 조건 |
|---|---|---|
| 차량 연결 | `Vehicle.initialize()`, `getDoor()`, `Vehicle.release()` | 비동기 연결·실패와 수명주기를 관리한다.[6] |
| 영역 확인 | `checkDoorPositionCapabilities` | `CapabilityConfig.accessType`과 영역별 `AreaBounds.minValue/maxValue`를 확인한다.[4][6] |
| 현재 문 상태 | `getCurrentDoorPosition` | 유효한 지원 영역의 현재값만 표시한다.[6] |
| 문 변화 구독 | `registerDoorPosition`, `unregisterDoorPosition` | 같은 Listener와 같은 영역으로 해제하며 등록 성공과 알림 수신을 구분한다.[6] |
| 최소 도어 권한 | `pleos.car.permission.CAR_DOORS` | 조회·구독에만 사용하고 제어 권한은 요청하지 않는다.[6] |
| 화면 사용 제한 | `CarUxRestrictionsManager`의 현재값 조회·구독·해제 | 화면 사용이 명시적으로 허용된 때만 주행 중 사용 최적화를 선언하지 않은 화면을 제공한다.[22][24][25] |

<p>표 5. 최소 기술 구성과 공개 계약의 대응.</p>

공식 Door 예제의 영역은 `ROW_1_LEFT`, 상태값은 Closed 0과 Open 1이다.[6] 후석 상수명·지원 차종·후석 두 영역의 알림은 실제 환경에서 확인해야 한다. 각 영역의 반환 범위를 확인하기 전에는 예제값을 일괄 적용하지 않는다. 미지원·조회 실패·초기값 미수신은 ‘미지원/확인 불가’로 표시한다. 운전석 문만 지원되는 경우 후석 제품 경험을 구현했다고 처리하지 않는다.

문 제어 `setDoorPosition`과 `CONTROL_CAR_DOORS` 권한은 제외한다. 내비게이션 도착, 위치, TTS/STT 음성 입출력, 원격 앱 연동도 최소 구현에서 제외한다. 필요한 범위의 템플릿 저장과 상태 처리는 로컬에서 수행하며, 제품 실행을 위해 서버 추론이나 사용자별 외부 API 호출을 요구하지 않는 구성을 계획한다.

### UX 제한과 상태 처리

[문헌] DO(Distraction Optimization)는 주의 분산 제한에 맞게 최적화된 화면의 선언이다. 본 앱은 DO를 선언하지 않는다. Pleos의 기본 정책은 DO 미선언 앱에 대해 Parking에서 허용하고 Drive에서 불허하며, 플랫폼 버전·양산차에 따라 달라질 수 있다.[23] Pleos는 `CarUxRestrictionsManager.registerListener()`와 `onUxRestrictionsChanged()` 연동을 직접 안내한다.[22] Google API의 `getCurrentCarUxRestrictions()`로 현재 제한을 조회하고 `registerListener()`·`unregisterListener()`로 구독을 관리한다.[24]

[가정·설계] 초기 화면은 잠금 상태로 시작한다. `isRequiresDistractionOptimization() == false`가 유효하게 확인된 경우에만 준비 화면 상호작용을 제공한다.[25] `getActiveRestrictions() == 0`만으로 허용하지 않는다. `UX_RESTRICTIONS_BASELINE == 0`이어도 DO 요구가 참일 수 있기 때문이다.[25] DO 요구가 참으로 바뀌거나 연결 해제·조회 실패로 상태를 신뢰할 수 없으면 상호작용을 중단하고 비-DO 화면을 닫거나 이탈시킨다. 단순히 버튼만 비활성화한 화면을 유지하는 것으로 제한을 충족했다고 간주하지 않는다. DO 요구가 거짓이면 비-DO 화면 표시가 허용된 상태로 판단한다. 이를 물리적 주차 완료나 안전한 하차의 증거로 쓰지 않는다.

문 상태는 다음 순서로 처리하도록 계획한다.

1. 화면 진입 때 세대번호를 발급한다. 이 번호는 이전 화면의 늦은 콜백을 구분하기 위한 값이다.
2. 읽기 가능한 각 영역에 Listener를 등록한 뒤 현재값을 조회한다. 등록 완료만으로 문 상태를 수신한 것으로 처리하지 않는다.
3. 조회 대기 중 같은 영역의 알림이 도착하면 늦은 조회 응답으로 알림값을 덮지 않고 재조회한다. 이전 화면 세대의 콜백은 무시한다.
4. 자동 강조 모드에서는 매핑된 지원 영역의 개방 이벤트를 고정 그룹 강조에 반영한다. 수동 선택 우선 상태에서는 모든 문 이벤트가 문 상태만 갱신한다. 항목 완료는 어느 모드에서도 사용자 입력으로만 기록한다.
5. 종료 때 동일 Listener·영역의 구독을 해제하고 수명주기 종료에서 `Vehicle.release()`를 호출한다. 재진입 때 과거 문 상태와 UX 허용값을 먼저 표시하지 않고 현재값을 다시 읽는다.

개발 검증에는 지연 조회 응답, 중복 알림, 이전 화면 콜백, 앱 재진입, 연결 해제, UX 제한 전환을 포함한다. 구독 해제 뒤 콜백을 무시하고 복귀 시 재조회하는지도 확인한다. 주행 제한 중에도 조작할 수 있거나, 문 닫힘으로 항목이 자동 완료되거나, 이전 세대 상태가 표시되면 수정 후 다시 검증하기 전에는 배포하지 않는다. 불필요한 제어·민감정보 권한, 네트워크 요청 유무, 앱 내 저장 기록 삭제도 점검한다. 이 기술 검증과 아래의 사용자 가치 비교는 별도 관문으로 관리한다.

## 6. 기대효과 및 발전 가능성

### 발견 조사와 공정한 비교

[가정] 반려견 동반 외출 사용자 10개 조, 총 20명을 모집하여 최근 외출의 역할·위치·사용 도구·중단 이유를 묻는다. 이후 동물 없이 같은 준비물을 쓰는 정차 모형 과제를 관찰한다. 실제 모집은 동의 절차를 준비한 후 수행하며, 앞좌석에 남는 역할을 연구자가 억지로 부여하지 않는다. 10개 조 중 6개 조 이상이 자연스러운 2인 분담·앞좌석 확인 흐름을 설명하고, 4개 조 이상에서 문 사이 중단·복귀가 반복될 때 고객 정의를 유지한다. 이 수치는 작은 발견 조사를 계속할 사전 기준이며 모집단의 비율 추정이 아니다.

설치·권한 안내·문별 항목 설정에 드는 시간과 번거로움을 중단 후 탐색 부담과 함께 조사한다. 첫 미확인 항목 탐색 3초 단축은 작은 목록에서 인지할 수 있는 차이를 검토하기 위한 잠정 실용 기준으로 둔다. 그러나 3초 이득이 설치·설정·협업 부담을 상쇄하는지는 아직 근거가 없다. 발견 조사에서 사용자가 느끼는 편익과 반복 외출 빈도를 함께 검토하여 비교 결과를 보기 전에 유지 기준을 확정한다. 작은 시간 차이만 얻고 설정 부담이 큰 경우 채택 근거로 삼지 않는다. 결과 확인 후 임계값을 변경해야 한다면 원래 기준의 결과를 보존하고 변경 분석은 탐색적 결과로 별도 기록한다.

### 유입과 지표의 분모

[가정] 첫 4주에는 반려동물 동반 여행 커뮤니티 2곳과 이동용품 판매처 2곳에 게시·무상 안내 협조를 요청한다. 커뮤니티별 30가구와 판매처별 20가구를 목표로 하되, 채널 간 중복까지 제거한 모집 후보 가구 N=100을 월별 모집 가정으로 둔다. 이 가구들은 아직 지원 환경이나 자연스러운 2인 동선을 통과한 가구가 아니다. 확보된 제휴·노출이 아니며 채널의 허가가 없으면 무단 게시하지 않고 모집 목표를 낮춘다.

같은 가구의 두 구성원, 여러 채널을 거친 같은 가구, 다중 설치는 한 가구로 센다. 동의 후 모집 담당자가 연구용 가구번호를 부여하되 제품 계정·차량식별자와 연결하지 않는다. 제품 자체는 연구용 가구번호를 수집하지 않는다. 최초 준비 확인을 완료한 대표 설치가 있는 가구를 활성 가구로 정의한다. 개인 참여번호로 집계하는 파일럿의 MAU(월간 고유 활성 이용자 수), 월 활성 설치 수, 월 활성 가구 수를 서로 구분한다.

### 예상 활성 가구와 재사용

N은 환경·동선 검사 전 중복 제거된 신규 모집 후보 가구 수이고, e는 지원 환경과 자연스러운 2인 동선을 모두 통과한 가구 수를 N으로 나눈 공동 통과율이다. i의 분모는 공동 통과 가구, a의 분모는 그중 설치 가구다. r은 이전 달 활성 가구의 다음 달 재사용률이다. 매달 이전 모집과 중복되지 않는 N=100가구를 확보할 때의 조건부 계산이며, 환경 통과율이나 동선 통과율을 e에 추가로 곱하지 않는다.

[가정·계산] 매월 신규 활성 가구 수는 U=N×e×i×a로 계산한다. 월별 활성 가구 수는 M1=U, M2=U+r×M1, M3=U+r×M2로 계산한다. 매달 새로운 100가구에 도달하고 재사용률이 일정하다는 예시이며 이미 확보한 수요가 아니다.

| 조건 | e / i / a / r 가정 | 신규 활성 U | M1 → M2 → M3 |
|---|---|---|---|
| 낮음 | 20% / 40% / 50% / 20% | 4가구다. | 4 → 4.8 → 4.96가구다. |
| 기준 | 40% / 50% / 60% / 40% | 12가구다. | 12 → 16.8 → 18.72가구다. |
| 높음 | 60% / 60% / 75% / 60% | 27가구다. | 27 → 43.2 → 52.92가구다. |

<p>표 9. 가정한 월별 활성 가구 수의 민감도. 소수는 조건부 기댓값이다.</p>

고유 개인 MAU는 활성 가구 수만으로 정해지지 않는다. [가정·계산] 같은 달 활성 12가구에서 각각 1명만 조작하면 12명, 각각 2명 모두 조작하면 24명이다. 이는 측정값이 아닌 단위 구분 예시다. 앱 계정이 없는 초기 단계에는 동의 기반 파일럿에서 개인·가구 단위를 구분하여 집계한다.

[가정] Retention Rate는 첫 핵심 행동 뒤 30일 관찰을 마친 고유 가구 중 다시 준비 확인을 수행한 가구 비율로 정의한다. 관찰 완료 가구가 20가구 이상이고 재사용률이 40% 이상일 때 확대를 검토한다. 같은 30일 관찰 기간에 적합한 2인 차량 외출이 다시 발생한 가구를 분모로 하는 상황 재사용률도 별도로 구한다. 이 분모가 10가구 이상일 때 60% 이상을 기준으로 둔다. 두 조건을 함께 본다. 발견 조사 10개 조와 장기 재사용 집단은 별개이며 필요한 가구 수에 도달하기 전에는 30일 판단을 하지 않는다. 두 차례의 모집에서 연속으로 기준에 미달하면 유료화·확대보다 중단을 선택한다. 본선 전 30일 관찰 완료를 약속하지 않는다.

| 월 유지비 회수 | 4만~8만 원÷3,430원을 각각 올림한다. | 월 신규 구매 12~24가구가 필요하다. |
| 구매 전 활성 | 고유 신규 활성 가구의 유료 전환율을 5%로 둔다. | 신규 활성 240~480가구가 필요하다. |
| 활성 전 노출 | 공동 통과율·설치율·첫 행동률의 곱 e×i×a=12%를 적용한다. | 환경·동선 검사 전 중복 제거된 신규 후보 가구 N=2,000~4,000이 필요하다. |

<p>표 10. 조건부 손익 규모. 실제 과금·수수료·세금·전환율은 확인 전이다.</p>

기준 모집의 월 신규 활성 12가구만으로는 독립 수익사업이 성립하지 않는다. 한 번 구매한 가구에 매달 다시 구매 비용을 청구하지 않는다. [가정] 필요한 규모를 검토할 확대 경로는 여행·이동용품 안내 채널 10곳이 각각 월 200~400가구에 안내하여 채널 간 중복까지 제거한 후보 가구 N=2,000~4,000에 도달하는 것이다. 채널당 수치와 합계는 모두 지원 환경·동선 검사 전 후보 가구 단위다. 이 수치는 계약된 유통망이나 예상 확보 고객이 아니라 손익 규모를 검토하기 위한 조건이다. 지원 환경과 자연스러운 2인 동선을 모두 통과하는 비율 e는 별도 관측하며, 실제 교차 채널 중복으로 N이 줄면 부족분을 확보한 것으로 계산하지 않는다.

2027년 1분기까지 작은 파일럿 채널 2곳의 전체 도달, 고유 가구 수, 지원 환경·동선 통과 수, 활성·구매와 지원 시간·비용을 확인한다. 10곳 확대 의향과 실제 단계별 통과율을 적용한 도달 규모가 손익에 필요한 수준에 못 미치면 유료사업 확대를 중단한다. 마켓 직접 유입이 생겨도 동일 가구 중복을 제거한 실제 추가분만 센다. 월 지원 시간이 4시간을 넘거나 공제율·고정비가 가정을 초과하면 손익분기를 재계산한다.

향후 템플릿 확대도 같은 판단 순서를 따른다. 반려견 외출에서 자연스러운 협업과 재사용을 확인한 뒤 다른 준비물 루틴의 필요성을 검토한다. 후석 지원 고객이 적거나 유통 증거가 부족하면 무료 연구 파일럿을 종료하고 유지보수 부담을 확대하지 않는다.
